Canonical Form（规范形）详解

为什么比对工具只查一次 hash 就能同时找到正、反链的匹配？以 bandmap / minimap2 为例

目录 1. 背景：DNA 是双链的 2. 问题：朴素的 hash 匹配会漏掉一半 3. 解决方案：canonical form 的定义 4. 为什么有效：等价类与确定性代表 5. 交互式演示 6. 代价与额外收获：strand bit 7. 在 bandmap / minimap2 中的完整落地 8. 常见疑问

1. 背景：DNA 是双链的

DNA 是双链分子，两条链通过碱基互补配对（A↔T, C↔G）结合，且方向相反 （一条 5'→3'，另一条 3'→5'）。所以任何一段序列 S 其实有两种"读法"：

  • 正向读出来：S
  • 读它的互补链（等价于把 S 做反向互补，Reverse Complement，记作 RC(S)）

这两种写法代表同一份序列内容。在比对工具（minimap2、bandmap 等）的世界里，query read 可能来自参考基因组任意一条链、任意方向——你事先不知道方向。

反向互补的机械规则

第一步：complement（每个碱基换成互补碱基）  A↔T, C↔G
第二步：reverse（整个串倒过来读）

例：  S     = A C G T
      compl = T G C A
      RC(S) = A C G T        （此例恰好是回文）

2. 问题：朴素的 hash 匹配会漏掉一半

比对的第一步是seeding：把 query 切成 k-mer，对每个 k-mer 计算 hash， 去参考序列的 hash 索引（index）里查找相同的 k-mer。命中即得到一个候选锚点（anchor）。

现在考虑一个具体场景：

问题场景

query 上有一个 k-mer ACG（k=3）。
参考基因组中，这段序列出现在负链上——意味着在索引建库时， 从正链读出来它是 CGT（ACG 的反向互补）。

如果你直接拿原始 k-mer 建 hash：hash(ACG) ≠ hash(CGT)， 查找失败。一个真实存在的匹配，就这么漏掉了。

一个自然的补救思路有两种，但都不理想：

方案做法代价
① 双份索引 把参考序列正向、反向互补各建一套 hash 索引 内存 ×2，索引构建时间 ×2
② 双向查询 query 每个 k-mer 用原始形式和 RC 形式各查一次 查询次数 ×2，seeding 时间 ×2

3. 解决方案：canonical form 的定义

Canonical form（规范形）：对 {S, RC(S)} 这一对序列 （它们代表同一内容），用一条确定性规则选出唯一代表，然后只存、只查这个代表。

最常用的规则（minimap2 / bandmap 采用的）：取字典序较小的那个。

canon(S) = min(S, RC(S))     // 字典序比较，按碱基编码 A<C<G<T

例（k=3）：
  S      = ACG
  RC(S)  = CGT
  ACG < CGT  ⇒  canon = ACG，strand bit = 0

例（k=3）：
  S      = CGT
  RC(S)  = ACG
  ACG < CGT  ⇒  canon = ACG，strand bit = 1   // 注意：代表相同，bit 不同！
核心性质

无论这段内容在链上以哪种方向出现，canon 计算结果完全相同。 于是正链上的 ACG 和负链上的 CGT 在 hash 空间里变成同一个 key—— 一次查找即可覆盖两个方向。

"canonical"（规范的、经典的）这个名字的含义：一个等价类里被规则钦定的 唯一规范代表。就像规定"集合 {+1, −1} 的规范代表是 +1"一样—— 代表不唯一才需要规则，规则确定之后等价类内所有成员归一到同一点。

4. 为什么有效：等价类与确定性代表

4.1 严格论证（两行）

需要证明：canon(S) == canon(T) 当且仅当 S == T 或 S == RC(T)。

  • ⇒ 方向：若 canon(S) == canon(T) == C，则 S、T 各自属于 {C, RC(C)}，所以 S == T（同向）或 S == RC(T)（反向）。
  • ⇐ 方向：若 S == T，显然 canon 相等；若 S == RC(T)， 则 RC(S) == RC(RC(T)) == T，于是 {S, RC(S)} == {T, RC(T)}， 两个集合相同 ⇒ 取 min 结果相同。

注意其中用到的关键恒等式：RC(RC(x)) = x（反向互补是 involution，做两次回到自身）。

4.2 一图看懂等价类

query 正链出现 ACG → 算 canon：min(ACG, CGT) = ACG，bit 0
↓ hash 相同，互相命中
index（负链读出）出现 CGT → 算 canon：min(CGT, ACG) = ACG，bit 1
↓
命中一个 anchor；相对方向 = bitquery ⊕ bitref = 0 ⊕ 1 = 反向匹配

两种朴素方案（双份索引 / 双向查询）能做的事，canonical form 用 1 次 hash 计算 + 1 次查找 + 1 bit 存储就做到了。

6. 代价与额外收获：strand bit

6.1 代价（非常小）

  • 每个 minimizer 多存 1 bit 的 strand 信息（放进 y 的最低位：y = pos << 1 | strand）。
  • sketch 时每个位置要同时计算正向 k-mer 和它的 RC——但两者本来就是用一个滚动编码同时维护的（sketch.rs:251-252），几乎没有额外开销。
  • 对称 k-mer（kmer[0] == kmer[1]，即回文）会被跳过：它没有方向信息，反正也匹配不到有用的位置。

6.2 额外收获：方向信息没有丢

canonical 化把绝对方向抹掉了，但选择过程本身留下了痕迹——strand bit。前面已经论证： 

相对方向 = strand_query ⊕ strand_ref
  0 → 两个序列同向对齐 → 产出"正向 anchor"
  1 → 反向对齐           → 产出"反向 anchor"（坐标反转 + MSB 置位）

换句话说：hash 层不区分方向（这是我们要的，为了省一倍查找）， strand bit 层记录方向（这是我们所需要的，为了正确 report）。 信息没有被扔掉，只是被延迟到 anchor 编码阶段才使用。

7. 在 bandmap / minimap2 中的完整落地

把前面所有环节串起来，就是 bandmap seeding 的完整数据流：

阶段做什么代码位置
sketch（query 和 ref 通用） 每位置算 kmer[0]、kmer[1]，取较小者为 canonical，记 strand bit 进 y sketch.rs:251-261
建索引 reference minimizer 按 canonical hash 存桶，命中记录带 ref strand 位 index.rs
seed collection 对每个命中比较 q_strand != r_strand：同向 → 正向 anchor；反向 → anchor 编码 1<<63 且 query 坐标反转 seed.rs:393-417
排序 按 x（MSB=strand）radix sort，数组自然分成"正向块 + 反向块" sort.rs:115
chaining DP 在反转坐标系里，反向链与正向链同样单调递增 → 一遍 DP 同时处理两个方向 chain.rs
整体等价性

这套设计与"对两个方向分别建索引、分别 seed、分别 chain"在结果上完全等价， 但只用了后者一半的索引内存和一半的查询次数。正确性由第 4 节的等价类论证保证； 方向恢复由 strand bit 的 XOR 性质保证；反向链可 chain 则由坐标反转的保序性保证。

8. 常见疑问

Q1：为什么选"字典序最小"，而不是别的规则（比如取 hash 较小者）？

任何确定性规则都行——正确性只要求"等价类内成员归一到同一点"，与具体选哪个无关。 选字典序最小的原因：(a) 计算零成本，比较两个已编码的整数即可；(b) 与 hash 函数解耦， 不会让 hash 分布特性影响 canonical 选择；(c) 同一规则天然适用于所有 k。

Q2：回文 k-mer（S == RC(S)）怎么办？

当 k 为偶数时可能出现，如 ACGT。它无法提供方向信息（strand bit 无意义）， 而且 sketch.rs:253 干脆跳过它。实践中回文 k-mer 极少且信息量低，丢弃无碍。

Q3：canonical form 会不会增加碰撞（不同序列映射到同一 key）？

不会引入额外碰撞。canon 是一个函数：canon(S) == canon(T) ⇒ S==T 或 S==RC(T)。 也就是说两个不同"内容"的 k-mer 的 canon 必不相同（哈希碰撞除外，而哈希碰撞本来就存在， 与 canonical 化无关）。它只是把"等价但写法不同"归并了，没有把"不同内容"归并。

Q4：RNA（如转录组比对）也这样吗？

minimap2 处理 mRNA 时用 --splice，原理相同：仍需处理两个方向的匹配 （转录本可能来自任一条链），canonical minimizer 一样适用；差别在下游 （剪接位点的 gap 罚分等）。此外 bandmap 还有一个 QSTRAND 模式 （seed.rs:403-409）：保持 query 坐标不反转、改为反转 reference 坐标， 用于需要保留 query 原始方向的短读场景——变的是"反转谁"，不变的是 canonical 化本身。

Q5：一句话总结？

Canonical form = 对"序列及其反向互补"这个二元素等价类做确定性归一化的唯一代表。 它解决的问题是：双链世界里"同一内容、两种写法"导致的 hash 匹配失败——办法是让两种写法 在 hash 空间不可区分，同时用 1 个 strand bit 保留恢复相对方向所需的全部信息。
