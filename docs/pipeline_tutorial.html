2管线总览

每一步的耗时占比（组1 全部 61 条 read，单线程）：Sketching ≈ 10%，Seeding ≈ 8%，Chaining ≈ 70%，Alignment ≈ 0%（种子扩展几乎不耗时），其余为后链过滤。

3Step 1 — Sketching：minimizer 提取

3.1 原理

序列不能直接存进索引，需要先压缩成一组"代表 k-mer"。bandmap 使用与 minimap2 完全一致的 (w, k)-minimizer 方案（sketch.rs::sketch_sequence_impl）：

  1. 把序列按窗口滑动，每个位置得到一个 k-mer（k = 12）及其反向互补 k-mer，取字典序较小的那个作为正则形式（这样无论序列出现在哪条链都能命中同一个 hash）；对称 k-mer 被跳过。
  2. 对正则 k-mer 的 2-bit 编码应用一个可逆混合哈希 kmer_hash（minimap2 同款）。
  3. 在宽度为 w = 5 的窗口内，哈希值最小的 k-mer 被选为 minimizer；哈希相同则取最靠右的。

直觉：普通 k-mer 索引每 ~1 bp 存一个条目；minimizer 的密度约为 2/(w+1) = 1/3，即每 3 bp 一个， 存储和查找成本降为 1/3，而只要两条序列共享的片段 ≥ w+k−1 = 16 bp，就必然共享至少一个 minimizer。

3.2 示例 read 的真实数字

这条 1,649 bp 的 read 产生了 557 个 minimizer（密度 1/2.96，正好符合理论值）。例如：

4Step 2 — Seeding：索引查找与 anchor 构建

4.1 索引里有什么

建索引时对 target 同样做 minimizer sketch：1,611 bp 的 target 得到 524 个 minimizer。 索引是一个 hash 表：hash → 该 hash 在 target 上的所有出现位置（附带链位）。 524 个 minimizer 只对应 415 个不同 hash：41 个 hash 出现了多次，合计多出 109 个重复条目 —— 这就是低复杂度序列的"重复种子"来源。

4.2 查找与 occ 过滤

对 read 的 557 个 minimizer 逐个查 hash，得到 254 个"有命中"的种子（303 个在 target 上不存在，直接丢弃）。 每个种子记录它的 hit_count（在 target 中的出现次数）。这条 read 的命中次数分布：

hit_count123479101114
种子数18022108833911

过滤阈值 mid_occ = 15（由索引自动标定：取 hash 出现次数分布的 99.98 分位（frac = 0.0002）的计数再加 1，下限 10；本例恰好落在最大 occ 14 + 1 = 15）。 所有种子的 hit_count ≤ 14，无一被过滤；select_seeds 的高频种子救援逻辑也因"不存在高频种子"而直接返回。 低复杂度数据在这里"逃过一劫"——如果 target 再长一点、重复再多一点，就会有种子被过滤。

4.3 anchor 构建

每个保留种子 × 每个索引命中 = 一个 anchor（种子匹配对）。总计 652 个 anchor（180×1 + 22×2 + … + 11×14 = 652），编码为 128-bit 的 Minimizer { x, y }：

x = ref_pos（正向命中）或 263 | ref_pos（反向命中）  ——  低 32 位，高 32 位 = rid
y = k-span ≪ 32 | query_pos（反向命中时 query_pos 做镜像变换，保证链化时"query 单调递增"对两条链都成立）

最后 anchor 按 x（ref 位置）做一次 不稳定的 MSD 基数排序（sort.rs::radix_sort_128x）， 为 DP 链化做准备。这条 read 的 652 个 anchor 中 646 个落在正链、6 个落在负链（负链的少量散点纯属低复杂度随机命中）。

5Step 3 — DP Chaining：动态规划链化

链化的目标：把 652 个散乱的 anchor 点连成若干条"共线链"（colinear chain）—— 即 ref 和 query 位置都单调递增、间距合理的 anchor 序列。这是整个管线中计算量最大的一步（组1 中占 ~70% 时间）。

5.1 输入排序与扫描窗口

anchor 已按 (ref_id_strand, ref_pos) 排序。DP 逐个处理 anchor i，向后扫描候选前驱 j（从 i−1 往回）。窗口受三个条件限制：

  • ref_id_strand 不同 → 出窗（正/负链的 anchor 永不混合）；
  • a[i].x − a[j].x > max_dist_x = 5000 → 出窗；
  • 窗口内 anchor 数 > max_chain_iter = 5000 → 截断。
关键观察：本实验的 target 只有 1,611 bp，而 max_dist_x = 5000 —— 窗口永远不会收缩，每条 read 的全部 anchor 都在彼此的窗口内。这是后面"负载问题"的根源之一。 在真实基因组（ Mb 级 contig）上，窗口只包含 5 kb 范围内的 anchor，密度低得多。

5.2 打分函数

对候选前驱对 (i, j)，chain.rs::compute_chain_score 计算"从 j 接到 i"的增量分：

qd = qi − qj（query 间距）， rd = ri − rj（ref 间距）， gw = |rd − qd|（gap 宽度）

先做合法性检查（不满足返回 −∞）： qd > 0；rd ≠ 0；qd ≤ 5000；同链时 gw ≤ bw(500)

sc = min(k-spanj, min(rd, qd)) − ⌊pen(gw)⌋
pen(gw) = chn_pen_gap·gw + ½·log₂(gw+1)　（chn_pen_gap = 0.8 × 0.01 × k = 0.096，由 finalize_options 按实际 k 算出；chn_pen_skip = 0）
⌊·⌋ 为向零截断（Rust as i32），惩罚恒为正，等价于向下取整

即：奖励 = 重叠长度（最多记 k-span = 12 分），惩罚 = 线性 gap 罚 + 半个对数罚。 三个真实算例（取自最优链相邻 anchor）：

(70,34)→(110,76)40422120.1920.793012

5.4 提前终止：visited / skip-break 机制（逐步详解）

如果每次都要扫完整个窗口，DP 就是严格 O(n²)。minimap2 式的提前终止依赖一个巧妙的计数器：

// chain.rs:412-432（简化）
for j in (window_start..i).rev() {
    sc = compute_chain_score(i, j);
    if sc == MIN { continue; }          // 非法候选：不计 skip、也不做 visited 标记！
    total = sc + scores[j];
    if total > best { best = total; pred = j;
       if skip > 0 { skip -= 1; } }     // 改善：撤销一次"放弃倾向"
    else if visited[j] == i {           // j 在本次扫描中已作为"某条链路径的上游"出现过
        skip += 1;
        if skip > max_chain_skip(25) { break; }
    }
    if preds[j] >= 0 { visited[preds[j]] = i; }  // 把 j 的前驱登记为"本轮已路过"
}

5.4.1 每个候选只有四种结局

结局触发条件skip 变化visited 标记本质
MINsc = −∞（qd ≤ 0、rd == 0、gw > bw…）不变不做（continue 在标记之前）打分白算，连计数资格都没有
IMPROVEtotal > 当前 best−1（仅当 >0）做找到更好前驱，"放弃倾向"被部分撤销
SKIP+1无改善 且 visited[j] == i+1；>25 → break做撞见一条"已经评估过的链路径"
no-effect无改善 且 visited[j] != i不变做最"浪费"的一步：分照算、计数器不动
visited 标记的准确语义：处理候选 j 之后执行 visited[preds[j]] = i —— 即"j 的 DP 前驱是本次扫描已经经过的路径节点"。 之后逆行到某个 j′ 时若 visited[j′] == i，说明 j′ 已经属于本轮评估过的某条链路径 —— 继续沿它向前大概率只是重复已知路径。 因此 skip > 25 的直觉是："我已经在 25 个属于已知路径的节点上毫无收获，放弃这片区域"。 注意计数器只被 IMPROVE 减 1（不是清零），MIN 与 no-effect 完全不参与计数 —— 这两点决定了低复杂度数据的行为（见 5.4.3）。

5.5 回溯：从分数到链

DP 结束后回溯（chain_backtrack）：

  1. 收集所有 scores ≥ min_chain_score(40) 的 anchor 作为候选，按分数排序；
  2. 从最高分候选出发，沿 preds 走回链头；途中用 z-drop（max_drop = bw = 500）防止回溯扫过超长 gap；
  3. 沿途 anchor 标记为已用，继续处理下一候选 —— 因此共享 anchor 的次优链会被截断；
  4. 链须满足 cnt ≥ min_cnt(3) 且自身分 ≥ 40，否则丢弃。

6Step 4 — RMQ rescue：为什么被跳过

默认情况下（minimap2 的 long-join 机制），DP 链化后如果 存在多条链（u.len() > 1）且最优链未覆盖 query 的较大部分（>1000 bp 未覆盖或覆盖 >10%），会用 bandwidth_long = 20000 做一次 RMQ（区间最值查询）重链化， 试图把相距很远的链"缝合"成一条长链（对应 read 中的超大结构变异/转置）。

本实验使用 --no-long-join（NO_LJOIN flag），该步骤整体短路跳过。

此前实验发现：对 ~1.7 kb 的短 query，rescue 的覆盖条件是恒真式（未覆盖 >1000 bp 与覆盖 >10% 两个分支必居其一）， 导致组1 全部 61 条 read 都白做一次 RMQ 重链化（~0.18 ms/read，总时间 +27%），且比对结果几乎不变 —— 这正是本教程的命令行加 --no-long-join 的原因。

7Step 5 — 后链过滤与比对输出

7.1 从链到比对区间

最优链的 anchor 跨度为 query 34–1645 / ref 70–1607（共 238 个 anchor，均分 1074 分）。 随后管线：

  1. Build regs + parent/filter：把每条链变成一个比对区间（region），按 score 筛主/次链（MAPQ 由主链分与次优分之差计算）；
  2. Alignment (Ext)：沿链做种子扩展 DP（affine gap + Z-drop），把 anchor 之间的小 gap 精确对齐，并向两端延伸到链外 —— 这就是为什么最终比对（query 23–1646 / ref 59–1608）比链跨度更长：左端各延伸 ~11 bp（34→23、70→59），右端各延伸 1 bp（1645→1646、1607→1608）；
  3. 输出 PAF。

三层放大效应：低复杂度 target ① 使每个 minimizer 命中多个位置（anchor 数 ×3.3）； ② 使 anchor 在 ref 上密集堆积、在 query 上方向混乱（skip-break 失效，扫描步数/anchor ×3.5）； ③ 两者相乘得到 ~11 倍的链化工作量。61 条 read 合计 258 万次打分计算，全部落在 70% 的链化时间里。
